# Baby Buddy Dashboard — React Native (Android)

A mobile dashboard client for a self-hosted [Baby Buddy](https://github.com/babybuddy/babybuddy) server (direct or via the Home Assistant add-on). Caregivers log diapers, feedings, medications, temperature, tummy time, and sleep for one or more children, see time-since-last stats and medication due/eligible windows, and run background timers.

**Design source of truth:** `design_handoff_react_native_app/README.md` (high-fidelity — colors, spacing, radii, copy, and interaction flows are final) **plus `CHANGES_SINCE_LAST_HANDOFF.md`, which supersedes it in the spots it lists** — the README was never refreshed after the prototype's 4-batch refactor, so read the two together. The interactive prototype `Baby Buddy Dashboard App.dc.html` is the behavioral reference; open it in a browser to verify conditional logic. Screenshots in `design_handoff_react_native_app/screenshots/` predate the refactor. Where the docs and the prototype disagree, **the prototype wins** (it corrected two spec errors — see `docs/DESIGN_REFRESH_PLAN.md` §1b).

**Build plan:** `docs/IMPLEMENTATION_PLAN.md` — phases, package rationale, API notes.

## Tech stack (decided — don't substitute without asking)

- **Expo** (managed workflow, latest SDK) + **TypeScript** (strict). Android is the only target for now.
- **React Navigation** (native stack) — 4 screens + modal sheet; no Expo Router.
- **Zustand** for client state (auth session, settings, running timers, form draft).
- **TanStack Query (React Query)** for all server state (children, entries) — no entries in Zustand.
- **AsyncStorage** for preferences; **expo-secure-store** for tokens/credentials.
- `@react-native-community/datetimepicker` for date/time fields.
- `@expo-google-fonts/nunito` + `expo-font` for typography.
- `react-native-svg` for the minimal geometric glyphs (custom-drawn, no icon library — pending design-owner sign-off, see plan).
- Jest + React Native Testing Library for tests.

## Project conventions

- All colors, spacing, radii, type sizes come from `src/theme/tokens.ts` — never hardcode a hex or px value in a component. Token values come from the handoff README's Design Tokens section (OKLCH already converted to hex there).
- Spacing scale only: 6/8/10/12/14/16/18/20/22/26/30. Radii: 8/10/12/14/16/20/24.
- Font weights map: 600 body, 700 chips/medium, 800 headings/buttons/values.
- Server data is normalized at the API-client boundary into internal entry shapes (`src/api/types.ts`); UI code never sees raw Baby Buddy or Home Assistant response shapes.
- Medication due/eligible math and feed grouping live in pure functions under `src/lib/` with unit tests — no date math inline in components.
- Timers are app-global state keyed by `{type, childId}`, persisted, and preferably backed by Baby Buddy's server-side timer endpoints — never form-local.
- Diaper Pee/Poo are two independent booleans (both can be on), not a segmented control.

## Commands

- `npx expo start` — dev server (press `a` for Android emulator).
- `npm test` — Jest.
- `npm run lint` / `npm run typecheck` — ESLint / `tsc --noEmit`.
- `npm run test:live` — integration suite against a real Baby Buddy server. Needs gitignored `.env.local` with `BABYBUDDY_URL` + `BABYBUDDY_TOKEN`; skips cleanly without it and is excluded from `npm test`. Uses its own `jest.integration.config.js` (plain node env — the jest-expo preset installs an Expo `FetchResponse` polyfill with no `.status`/`.ok`, which makes every request look like a failure).
- Quick visual QA without an emulator: `npx expo export --platform web --output-dir <dir>` then serve it, or `npx expo start --web`. `react-dom`/`react-native-web` are installed for this preview path only (target stays Android). On web, Reanimated's animation loop can make browser screenshots time out — verify via DOM text if so.
- **Web can only run against `USE_MOCK_DATA`.** Baby Buddy sends no `Access-Control-Allow-Origin`, so a browser blocks every API response. Real-server testing means Expo Go or a device build.

  - **Server-time rules — the big gotcha.** Baby Buddy's `validate_time()` rejects anything past the *server's* clock, and `validate_duration`/`validate_unique_period` reject inverted, >24h, or overlapping windows. So: never stamp an entry with the device's `Date.now()` — use `serverNow()` from `client.ts`, which tracks the offset from each response's `Date` header (the test server trailed by ~1.3s, which was enough to break every "now" entry). And never send `end = start + duration` from a "now" start — `resolveWindow()` in `normalize.ts` slides the window back to end at now, preserving the duration. `Note` is the only model with no `clean()`, so it is not a good smoke test for timing bugs.
  - **Boot must never gate on storage succeeding.** `App` renders nothing until `hydrated`; `onRehydrateStorage` sets it on both success and error, `secureStorage` swallows read/write failures, and `App` has a 5s boot timeout. A secure-store read that throws used to hang the app on a blank screen.
- **Phase 6 done, verified against a live server** (`npm run test:live`, 11/11). Timers are backed by `/api/timers/`: `getTimers`/`startTimer`/`stopTimer` on the `DataSource`, wire mapping in `normalize.ts`, React Query hooks in `data/queries.ts`, and `src/hooks/useTimers.ts` composing store + server (`useTimerSync` mounted in `RootNavigator`, `useTimerActions` used by `TimerControl` and `LogEntryScreen`).
  - **The server model is thinner than the docs suggest.** A Timer is `{id, child, name, start, duration, user}` — no `active`, no `end`, so **stopping = DELETE**, and `/api/timers/{id}/restart/` is **405 on this server** (don't build on it). The server permits several timers per child; one-per-(type, child) is ours to enforce.
  - **Don't create entries via the `timer:` reference.** It works and auto-deletes the timer, but it **ignores an explicit `end`** and forces end = now — which would silently discard a user-edited end time. Saving keeps the Phase 5 explicit start/end path (`resolveWindow` + `serverNow`) and deletes the timer afterwards.
  - **Local store drives the UI, the server makes timers durable.** Start/stop write the store first and call the API after, so a timer never waits on the network; a failed create leaves a local-only timer that still runs and still produces an entry. `reconcileTimers` in `src/lib/timers.ts` is the whole merge: *a local timer is discarded only when it claims a server id the server no longer lists.* `timerStore.stopping` (not persisted) holds ids whose delete is in flight so a slow stop can't re-adopt the timer on the next poll. Timers with an unrecognised name or no child are ignored, never adopted — the live server already has one from another client.

- **Multi-language (English + Hebrew).** All user-facing copy lives in `src/i18n/locales/{en,he}.ts` behind i18next (`react-i18next`). The instance in `src/i18n/index.ts` **self-initializes synchronously on import** with inline resources, so pure helpers in `src/lib`/`src/api` can call `i18n.t(...)` immediately — including under Jest with no provider mounted. That's the load-bearing trick: the `en` values are byte-identical to the strings those helpers used to return, so the existing string-assertion tests stay green once i18n is initialized. Components use `useTranslation()`, which also subscribes them to language changes so the whole tree re-renders (and the pure-helper labels recompute) on a switch. Any module-scope option array that had a label was moved into render, or its labels would freeze at import time. The former label maps (`entryTypeLabel`, `feedingKindLabel`, `DOSE_UNITS.label/suffix`, `solidFoodTypeLabel`, …) are now **functions**, not objects. Node/Jest has `Intl` built in, so this only shows up on the RN target, not in tests. Wire-format strings are deliberately **not** translated: the `by {creator}` author tag and the `as-needed`/temp-method/`__key:value` reserved tags are serialization, parsed by prefix, and must stay literal. **`Child.age` was the one baked display string** — it's computed in `normalize.ts` at fetch time and cached by React Query, so it didn't relocalize on a switch; `Child` now also carries `birthDate` and `ChildCard` recomputes `ageLabel(birthDate, now)` at render (the `age` snapshot stays for the normalized API contract / live test).
- **Notifications (local-scheduled).** `expo-notifications`, no push backend — a self-hosted Baby Buddy can't reach the device, so every reminder is a *future timestamp we can compute now* and the plan is rebuilt/re-scheduled on data change, app-foreground, and a 60s interval. Pure planner `src/lib/notifications.ts` (`buildNotifications`, unit-tested, never imports the native module) → native wrapper `src/notifications/service.ts` (no-op on web/Expo Go, like `secureStorage`; sync = cancel-all + reschedule) → `useNotificationSync` (in `RootNavigator`) → persisted `notificationStore` → `NotificationSettingsScreen`. Cases: scheduled meds, med eligibility, forgotten timers (before/at/after timing model), diaper-interval + food-min (per-child, single-fire). **Needs a dev/EAS build to actually fire** — unverifiable in Expo Go/web; the live/ongoing-timer notification is deferred (needs an Android foreground service, out of the managed workflow).
  - **Server-validated delivery** (this feature). The rule: **no reminder reaches the user on a premise the server no longer backs.** Baby Buddy is multi-caregiver, so cached data goes wrong on its own — another parent logs the change and our "diaper check" is about to lie. Three gates, all routed through one pure `validateNotification` (`src/lib/notificationValidation.ts`, 19 tests) and one shared `useNotificationValidator` hook: (1) *plan time* — the rebuild `await`s `refreshServerData(queryClient)` (new, in `data/queries.ts`) before building, so the plan is never derived from whatever React Query happened to be holding; (2) *delivery time* — `service.setDeliveryValidator` gives the native handler a gate that refetches and re-derives the reminder as it arrives, suppressing it if the premise is gone; (3) *the in-app carousel* — `useDeliveredNotifications` re-validates the tray on open, which is the **only** chance to catch a reminder that fired while the app was dead, and dismisses the false ones from the tray too.
    - **The unclosable gap, stated honestly:** a local notification firing with the app killed cannot be intercepted — `expo-notifications` only runs a background task for *remote push*, which a self-hosted server can't send (the reason this feature is local-scheduled at all). So gate 2 is **foreground-only** and the real guarantee off-foreground is "validated as of the last successful sync", with gate 3 cleaning up on next open. A periodic background revalidation task (`expo-background-task`) would shrink that window; not added, as it's a new native dep.
    - **Fail open, with a disclaimer.** When the server can't be reached the reminder is still shown — silently swallowing a medication reminder every time the VPN drops is the worse failure — but its body is wrapped by `withDisclaimer`. That helper is **idempotent** (planned offline *and* delivered offline must not stack two caveats) and detects an already-marked body by rendering the template with an empty `{{body}}` to recover the marker, so it works in either locale and regardless of where the sentence puts the caveat. Conversely a *confirmed* delivery returns the freshly-built body, which **removes** a disclaimer baked in at plan time.
    - **Validation re-derives the plan instead of hand-checking each case.** `buildNotifications` was split over a new `buildCandidates` (unfiltered), and validation is "is this key still a candidate, and has its anchor moved into the future?" — so a *new* reminder case is validated for free, where per-case rules would silently drift from the planner they guard. Two things this makes subtle: **`WEEKLY_KEY` must skip the fireAt test** (at the instant it fires, `nextWeeklySlot` has already rolled forward 7 days, so every weekly recap would read as stale), and a 60s `TOLERANCE_MS` absorbs scheduler jitter — safe because a real data change moves a deadline by minutes at minimum.
    - **Notification content is immutable at delivery,** so the only way to show corrected copy is to suppress the original and re-present an amended one. That's done under the **same identifier** (keeps the key parseable by `notificationAction`/the carousel, and makes a visible duplicate structurally impossible) with a `revalidated: true` data flag — without which the re-presented copy would re-enter the handler forever. `ongoing:`-prefixed notifications bypass the gate entirely: they're presented by us each minute from live state, so validating them would fight their own refresh loop.
  - **Weekly caregiver-contribution summary.** A 6th case: once a week it recaps what *you* logged per category over the trailing 7 days and your share vs. the **other caregivers on the same server** — the buildable reading of a "compare with other users" ask, since Baby Buddy is self-hosted with no cross-server aggregation and no donation/payment data. "You" = `session.userName` matched to `entry.creator` (the `by {creator}` author tag), threaded in as `me`. Pure math + localized body in `src/lib/contribution.ts` (`computeContribution`/`contributionBody`); scheduling via `nextWeeklySlot(now, weekday, hour)` (local-time slot). **Two structural departures from the other cases:** it's **horizon-exempt** — `key === 'weekly'` bypasses the 48h filter because the slot is up to a week out — and its **body joins the reschedule signature** in `useNotifications.ts`, because `fireAt` is fixed all week so the recap must re-sync as the trailing-week counts change (the other cases have fireAt-stable bodies, so this adds no churn for them). The body is a snapshot re-taken each rebuild → accurate as of the last app-open before it fires. Skipped when nothing was logged all week (`allTotal === 0`) or `me` is empty; a solo caregiver gets a comparison-free `weeklyBodySolo` variant (a "% of the family" line would be meaningless). Setting `weeklySummary {enabled, weekday, hour}`, default **on**, Sunday 9am — the toggle is the opt-out; day-chips + hour Stepper on `NotificationSettingsScreen`.
- **Kids visibility & advanced settings.** Which children show on the dashboard, and how they're coloured — all **client-only, device-local** (Baby Buddy has no visibility/group/colour concept), layered over the normalized `Child` at the UI boundary, never on the `Child` type. Persisted `kidsStore` (`hidden`, `childGroupId`, `childAccent`, `childSchedule`, `groups`, `defaultVisibility`, `knownChildIds`, `shakeReveal`; full shape defined up front so later UI needs no migration, like `notificationStore`'s deferred cases). Pure, unit-tested math in `src/lib/visibility.ts` (`isChildHidden`/`visibleChildren`/`isScheduleActive`/`effectiveHue`/`hiddenCount`/`newChildIds`, 16 tests) takes `now` as an arg and never imports the store. The dashboard filters `children` through `visibleChildren` on the **existing minute tick**, so a schedule boundary re-filters within a minute with no new ticking infra.
  - **One group per child; colour precedence `childAccent ?? group.accentHue ?? child.hue`.** Accent is a single **hue** (curated `ACCENT_SWATCHES`, no free colour wheel) run through `accentColors(hue, scheme)` in `src/theme/accent.ts`, which drives avatar + name + a `Card` gradient (new optional `gradient` prop backed by `expo-linear-gradient`). Both schemes are live — `accentColors(hue, scheme)` takes the scheme from `useTheme()` at the call site (see the dark-mode section below).
  - **Scheduling = daily window + weekday chips**, "hidden during the window". `startMinute > endMinute` wraps past midnight; empty `weekdays` = every day. Both per-child (`childSchedule`) and per-group (`group.schedule`).
  - **Default visibility for new kids** via `useApplyDefaultVisibility` (mounted in `RootNavigator`): a child id not in `knownChildIds` is newly-seen — hidden if the default says so, then recorded. Idempotent, so it never re-hides an unhidden child; a fresh install records everyone as known while the default is `visible`, so switching to `hidden` only affects *later* arrivals.
  - **Reveal = shake + button.** `expo-sensors` accelerometer in `useShakeDetector` (no-ops where the sensor is absent — web/emulators — which is why the manual button ships too; works in Expo Go, unlike notifications); `useShakeReveal` only listens while the pref is on AND something is actually hidden. Reveal state is a session-only `revealHiddenUntil` timestamp in **`uiStore`** (not `kidsStore`, not persisted — a relaunch shouldn't stay revealed); a dashboard `setTimeout` re-hides exactly at expiry. The "Show N hidden children" chip and shake both call `uiStore.revealHidden(ms)`.
  - **UI:** per-child hide toggle in `SettingsScreen` (quick access) + an "Advanced" nav row → `AdvancedSettingsScreen` (default visibility, shake enable/duration, groups list, always-complete kids list) → `KidEditorScreen` / `GroupEditorScreen` (accent `AccentPicker`, group assignment, `ScheduleEditor`, hide). Verified end-to-end on web+mock (hide→tab row collapses + "Show 1 hidden child" chip→reveal restores both; Advanced/Kid/Group editors + schedule + swatches render). `ToggleSwitch` gained an optional `accessibilityLabel`. **Gradient colours can't be eyeballed on web** (Reanimated stalls browser screenshots) — the gradient is deterministic HSL math and the bundle compiles, but on-device colour QA is still worth a glance.
- **Dark mode (light / dark / system).** Persisted `themeStore` holds the *preference* (`'system' | 'light' | 'dark'`, default `system`); `useEffectiveScheme` resolves it against RN's `useColorScheme()` at render and `App` feeds the result to `ThemeProvider`. Storing the preference rather than the resolved scheme is deliberate — persisting the resolved value would freeze a `system` user to whatever the OS was on the day they last opened the app. Picker sits in Settings beside the language chips (`settings.appearance*` in both locales).
  - **The whole cost of this feature was that colour used to be a constant.** `colors`/`tints` were module-scope objects baked into 36 `StyleSheet.create` calls across 43 files, and `StyleSheet.create` snapshots values at import — so a runtime switch does nothing to an already-created sheet. Colour moved out of `tokens.ts` into `palette.ts` (`PALETTES.light` / `PALETTES.dark`, frozen one-per-scheme so `useThemedStyles` has a stable memo key); `tokens.ts` keeps only the scheme-independent spacing/radii/type scale. The migration pattern is `const { colors } = useTheme()` + `const styles = useThemedStyles(makeStyles)` with `const makeStyles = ({ colors }: AppTheme) => StyleSheet.create({...})` — destructuring to the same names in both places meant the ~295 individual colour *references* never had to change, only imports and wrappers. Six stylesheets that contain no colour were deliberately left static.
  - **Removing the `colors` export was the migration tool.** Deleting it from `tokens.ts` turned `tsc` into an exhaustive checklist of all 41 affected files; a compatibility shim would have let files silently stay light. Worth repeating for any future theme-wide change.
  - **Two escape hatches from the hook, both intentional.** `src/lib/entryDisplay.ts` is pure and hook-free (like the `i18n` singleton it already uses for labels), so `entryTint`/`entryVisual` take an optional `scheme` defaulting to the module-level `getScheme()`; components that hold a theme pass `theme.scheme` explicitly, tests omit it and get light. The ~25 glyphs default `color` to `themeColors().textPrimary` — a *default parameter* is evaluated per call, so it tracks the scheme without giving every glyph a hook.
  - **Dark is authored, not spec'd.** Neither the handoff nor the prototype has any dark spec, so the palette was derived from light on one rule: keep the warmth (warm near-black browns, not neutral greys; every pastel tint becomes a deep desaturated version of the same hue). Two values invert rather than translate: `onAccent` is white on light but **dark** on dark (the lifted accent is too light for white text), and `textSecondary` is *darker* than `textMuted` in light but *lighter* in dark, because the pair means "more/less emphasis". The `black` stool swatch is the one unfaithful value — a near-black swatch on a near-black card is indistinguishable from *no swatch*, which is what a missing colour looks like, so dark uses the darkest warm grey that still reads as filled.
  - **Elevation had to change form.** A drop shadow is invisible against a dark surface, so the dark palette carries `cardBorder` and `Card` draws a hairline outline keyed off it being defined. Light leaves it `undefined` rather than `'transparent'` — a transparent border would still inset the light layout by a hairline. `palette.test.ts` guards the key parity that this asymmetry deliberately breaks.
  - **The failure mode the tests exist for:** a colour key present in light and missing in dark resolves to `undefined`, which RN renders as *transparent* rather than throwing — invisible in light mode, in every test, and only wrong on a dark device. `palette.test.ts` asserts key parity and non-empty values in both schemes; `entryDisplay.test.ts` runs its every-entry-type case under both.
  - **Verified on web + mock data:** system-follow picks up the OS scheme at boot; tapping Dark with the OS on light flips the whole tree with no reload and persists; a DOM sweep for the light palette's signature colours found **zero** leaks across the dashboard (515 elements) and the log-entry form (623), with text inputs correctly re-coloured. Live scheme *changes coming from the OS* couldn't be exercised — CDP media emulation updates `matchMedia().matches` without delivering the `change` event — so the `system`-preference-plus-OS-toggle-while-running path is the one thing still unproven on a real device. `.claude/launch.json` now defines the `expo-web` server for this QA path.

Reanimated 4 requires `react-native-worklets/plugin` in `babel.config.js` (already set). Its Jest mock is deliberately omitted from `jest.setup.js` until a test renders an animated component (it fails eagerly under jsdom otherwise).

`react-native-worklets` is pinned to an **exact** version (no caret) because the Babel plugin stamps `__pluginVersion` onto every worklet and the runtime throws `[Worklets] Mismatch between JavaScript code version and Worklets Babel plugin version` if it doesn't match the installed lib. Two ways to hit that: letting the version drift (always install it via `npx expo install`, which pins the SDK's version), or a stale Metro cache holding worklets transformed by the previous plugin. After any change to worklets/reanimated versions, start with `npx expo start -c` — a plain restart reuses the cache and the error persists.
